# Report registration time

Business question: **How long does the application take to register a new lost or found item report?**

## Current integration

ItemViewModel now wraps the report operation with the existing tracker.
Home's **I found an item** card opens ReportItemScreen(reportType: 'found').
The same form supports reportType: 'lost' for future navigation integration.
ItemDao writes directly to foundItems or lostReports using the authenticated UID;
LostReportRepository and FoundItemRepository continue to handle reads.
No samples are seeded or generated by opening the dashboard.

## Measurement boundary

The form validates before calling ItemViewModel.reportItem. After checking the
current Firebase user's UID, the ViewModel calls tracker.measure with the chosen
reportType. Timing includes GPS acquisition, building ItemModel, the found-report
semester lookup and the awaited Firestore write. It excludes form completion,
validation and analytics persistence. There is no image upload in this flow.

ItemDao reads appConfig/general.currentSemesterId for found reports, falling back
to 2026-2 for a missing or malformed value. Configuration read failures and GPS
or report write failures fail the operation and produce no successful sample.
No Stopwatch logic is placed in the Widget.

The tracker starts a fresh monotonic Stopwatch immediately before invoking the
operation and stops it immediately after success. It returns the original result.
If the operation throws, it stops timing, records nothing and rethrows the
original exception and stack. Invalid report types are rejected before timing or
calling the operation.

After success the tracker attempts a metric write without awaiting it. This
keeps pending offline writes from delaying success navigation. Write errors are
contained: no rollback, fatal error or resubmission. There is one write attempt
per successful measure call and no tracker retry. This is best-effort telemetry;
closing the app before persistence completes can lose a sample. It is not an
exactly-once backend audit log.

## Firestore schemas

`performanceMetrics/{autoId}` contains exactly:

| Field | Value/type |
| --- | --- |
| metricType | `report_registration` |
| reportType | `lost` or `found` |
| platform | `flutter` |
| durationMs | Nonnegative integer, elapsed milliseconds |
| recordedAt | `FieldValue.serverTimestamp()` |

No identity, report ID, item details, location or image information is accepted by
the metric writer.

`analytics/reportRegistrationTime` contains exactly:

| Field | Value/type |
| --- | --- |
| sampleCount | Total valid samples, integer |
| averageMs | Mean across all valid samples, number or null |
| lostCount | Valid lost samples, integer |
| lostAverageMs | Lost mean in milliseconds, number or null |
| foundCount | Valid found samples, integer |
| foundAverageMs | Found mean in milliseconds, number or null |
| updatedAt | Firestore Timestamp for the injected refresh time |

The aggregation service queries metricType == report_registration from the
server, filters platform == flutter, known report types and finite nonnegative
numeric durations. Fractional numbers are accepted when reading samples, though
the tracker writes integer milliseconds. Malformed samples are ignored. Each
sample has equal weight in the overall average. Running means avoid sum overflow.

Refresh replaces only the aggregate document. It does not modify samples or
reports. Repeated refreshes recalculate from the source instead of accumulating
counts. A failed source read cannot overwrite the aggregate using offline cache.
Read/write errors propagate to the ViewModel, which retains the last successful
summary and presents a retryable error.

## Dashboard

Staff access opens AnalyticsDashboardScreen. Panel order is Report Bottleneck,
Report Registration Time, then additionalPanels. Each panel has independent state
and its own Refresh analytics button. Opening the registration panel only reads
analytics/reportRegistrationTime through ReportRegistrationTimeRepository.
Refreshing uses ReportRegistrationTimeAggregationService and displays the result
after the aggregate write succeeds.

Milliseconds are displayed as seconds with two decimals. Zero valid samples
produce zero counts, null averages and **No registration measurements yet**.
A missing type shows **No measurements yet** for that type, with its count of
zero. A missing aggregate has a distinct not-generated message and a Refresh
button; it is not treated as a measured zero-second result.

To verify with real registrations, sign in as a student, open **I found an item**,
fill in title, description and category, then submit and grant location access.
After success, open Staff Analytics and press the registration panel's Refresh
analytics button. Production code does not insert examples. No live Firestore
data was created during implementation.

## Rules status and minimal eventual permissions

No Firestore rule files are present locally, and firebase.json has no Firestore
rules configuration. Deployed permissions cannot be inferred from this checkout.
No rules were changed or deployed. The teammate owning backend rules must inspect
the existing rules and role checks before making scoped additions:

- `performanceMetrics/{id}`: allow **create** for authenticated users authorized
  to submit reports. Require exactly the five sample fields, fixed metricType
  and platform, reportType in lost/found, an integer durationMs >= 0, and
  recordedAt equal to request.time (server timestamp). Do not allow client
  update/delete. Allow admin reads needed by aggregation; student reads are not
  needed.
- `analytics/reportRegistrationTime`: allow admin **get**, **create** and
  **update** on this exact document, with exactly the seven aggregate fields.
  Validate nonnegative integer counts, sampleCount == lostCount + foundCount,
  finite nonnegative numeric means for nonempty groups and null means for empty
  groups, plus an updatedAt timestamp. No student access, collection-wide write
  permission or delete permission is needed.

Reuse the existing authoritative admin/submitter authorization checks. Review
overlapping rules because an existing broader allow can defeat a narrower rule.
Do not introduce a second role system or grant access to every analytics document.
These client metrics describe application observations; authenticated clients
can still submit fabricated durations. Server-trusted measurements would require
a backend design beyond this phase.

Stopwatch instances cover successful and failed registrations, nonblocking metric
